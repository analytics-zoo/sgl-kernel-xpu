# Build time analysis — sgl-kernel-xpu on Intel Arc Pro B60

Notes on where `pip install -v .` spends its time and how to make iterative
builds faster. All numbers are from this fork on a 7× Arc Pro B60 host with
oneAPI 2025.3 / PyTorch 2.11.0+xpu / Python 3.12 / `MAX_JOBS=8`.

## TL;DR

A full clean build ≈ **30–40 min**. The dominant cost is **SYCL device-code
compilation** (~30 min on 647 translation units). The `cutlass-sycl`
`FetchContent` re-clone and AOT ocloc GEN-ISA generation are secondary.

Most of the time waste in this fork has come from **unnecessary
`rm -rf build`** between iterations. Skipping that cuts iteration time to
a few minutes when only `.py` / `.cmake` / localized `.cpp` changed.

## Where the time goes

Last full build finished at `[647/647]`, split roughly:

| Stage                                              | Time        | Notes                                                                 |
|----------------------------------------------------|-------------|-----------------------------------------------------------------------|
| 1. CMake configure + FetchContent cutlass-sycl     | ~1–2 min    | `git clone` the 20k-file `intel/sycl-tla` repo (GIT_SHALLOW OFF)      |
| 2. Kernel-instance `.cpp.in` template expansion    | ~30 s       | FMHA / MLA / GroupGEMM per-(dtype, head_dim, page_size) instances     |
| 3. SYCL kernel compilation (`icpx -fsycl -fsycl-targets=spir64_gen`) | **~25–30 min** | 647 TUs × 8 parallel, each does heavy cutlass template expansion |
| 4. Link → `libsgl-ops-sycl-*.so` (216 shared libs) | ~2–3 min    | One `.so` per kernel source (upstream convention)                     |
| 5. AOT GEN-ISA generation via ocloc for BMG         | ~5–10 min   | `-Xsycl-target-backend=spir64_gen -device bmg` per Xe20 target        |
| 6. Wheel pack + pip install                         | ~10 s       | `.so` files + python/ copied into wheel and dropped into site-packages|

(If the vendored `GdnAttn.cmake` is enabled, add ~2 TUs to stage 3 and
one more ocloc pass to stage 5 — roughly +3 min.)

Stage 3 is dominated by cutlass-sycl template expansion: each TU pulls in
`cute/tensor.hpp` + collective mainloops + epilogues and emits SPIR-V
artifacts. A single TU (e.g. `xe_fmha_fwd_decode_kernel_16_256_128.cpp`)
takes 30–90 s on icpx.

## What `rm -rf build` throws away

Every full-clean rebuild discards:

1. **`build/_deps/repo-cutlass-sycl-src/`** — 30k-file checkout, re-clones on next CMake configure (~60 s over internal proxy).
2. **`build/src/CMakeFiles/*.dir/*.o`** — 647 compiled object files. Ninja's dependency scan is what keeps these valid across re-configures; wiping `build/` forces all 647 back through stage 3.
3. **`build/src/CMakeFiles/*.dir/*_device_obj.o`** — intermediate SYCL device-code link products (produced by `FindSYCL.cmake`'s `SYCL_LINK_DEVICE_OBJECTS`). Rebuilt whenever any object in a library changes.
4. **`build/src/*.so`** — 216 shared-library link products.
5. **AOT-cached GEN ISA blobs** — regenerated by ocloc every build.

#1 and #2 are by far the most expensive to reproduce.

## Fast iteration workflows

### A. Incremental (the default you want)

Don't delete `build/`. Ninja picks up CMake / source changes and only
recompiles what's affected:

```bash
cd /llm/workspace/sgl-kernel-xpu
# no rm -rf build/
pip install --no-build-isolation -v .
```

Typical times after an incremental change:

| Change                                  | Rebuild cost                                  |
|-----------------------------------------|-----------------------------------------------|
| `python/sgl_kernel/*.py`                | ~30 s (no compilation, wheel rebuild only)    |
| `src/CMakeLists.txt` / `*.cmake`        | ~1–2 min (CMake reconfigure + nothing rebuilt unless source set changed) |
| One `src/sycl/*.cpp`                    | ~2–5 min (that one TU + its `.so` relink + ocloc for its target) |
| One `src/gdn_attn/*.cpp` (vendored)     | ~2–5 min (same pattern)                       |
| Add a new file to `file(GLOB …)`        | ~3–10 min (ninja regenerate + new TU + new `.so` + ocloc) |
| New compile define added to whole target| Near full rebuild (3 forces TU rebuilds)      |

### B. Selective clean (preserve cutlass, wipe the rest)

When CMake state goes weird (e.g. after branch switching) but you don't
want to re-fetch cutlass:

```bash
cd build
rm -rf CMakeFiles/ src/ CMakeCache.txt build.ninja \
       *.cmake cmake_install.cmake .ninja_deps .ninja_log
# build/_deps/ (cutlass) stays
cd ..
pip install --no-build-isolation -v .
```

Saves the 60-second cutlass re-clone and gets a clean configure.

### C. Full clean (what we'd been doing)

Only when you hit actual CMake generation failures or change `CMakeLists.txt`
in ways that affect FetchContent:

```bash
rm -rf build/
pip install --no-build-isolation -v .
```

### D. Switching cutlass revision

FetchContent caches under `build/_deps/` keyed on the declared `GIT_TAG`.
Changing the tag triggers a re-checkout automatically (~30 s); no need to
delete anything.

## Build isolation

We use `pip install --no-build-isolation`. This reuses the outer venv's
`scikit-build-core` / `ninja` / `cmake`. Without it pip creates a
throwaway build-venv every time, which slows things down **and** drops the
ccache / ninja state.

If scikit-build-core is missing in the venv:
```bash
pip install scikit-build-core ninja wheel
```
(Done once per fresh container; persisted afterward.)

## Parallelism

We default to `MAX_JOBS=8` / `CMAKE_BUILD_PARALLEL_LEVEL=8`. Each icpx
worker peaks at 2–4 GB RSS during cutlass template expansion. On this
128 GB host 16 workers might cut stage-3 time ~40 %:

```bash
export MAX_JOBS=16
export CMAKE_BUILD_PARALLEL_LEVEL=16
```

Risk: if OOM then ninja kills random children and the build fails
mid-way; you'll want to re-run in `MAX_JOBS=8` to finish. I've kept the
default conservative; bump when experimenting.

## ccache / sccache

Not currently wired. Two reasons:

- SYCL device-code compilation hashes the whole cutlass template
  instantiation. Most 647 TUs generate unique internal types (different
  tile shapes), so cache hit rate across TUs is ~0. Across re-builds of
  the same TU, ccache would help — but ninja already handles that via
  timestamp-based incremental builds (workflow A).
- sccache's SYCL (`icpx`) support is incomplete; cache-hashing the full
  device-code linker chain is not covered.

If someone wants to try: set `CMAKE_CXX_COMPILER_LAUNCHER=ccache` before
configure. Unlikely to pay off for the SYCL work; might help host-side
`.cc` bindings which are trivially small.

## Rough time budget on this host

For a developer iterating on `src/gdn_attn/*.cpp`:
- First build ever (fresh container): **~35 min**
- Edit one `.cpp`, rebuild: **~3 min**
- Edit `.py` wrapper, rebuild: **~30 s**
- Edit `CMakeLists.txt` to add a file: **~5 min**
- Switch `CUTLASS_REVISION`: **~30 min** (full re-expand)
- `rm -rf build/` after: **~35 min** (avoid unless necessary)
